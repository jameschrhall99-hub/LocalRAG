# Judge calibration and human review

## What this adds

The existing RAG evaluator uses an uncalibrated model to judge reference correctness and evidence support. This step adds a labelled-example review workflow and a separate assessment of how well that judge classifies known examples.

There are **80 proposed examples**:

| Task | Calibration | Validation | Total |
|---|---:|---:|---:|
| Claim support | 36 | 24 | 60 |
| Reference correctness | 12 | 8 | 20 |
| Total | 48 | 32 | 80 |

Support labels are balanced across supported, contradicted and insufficient. Correctness labels are balanced across correct and incorrect. The examples include paraphrases, changed facts, negation, irrelevant excerpts, unsupported guarantees, a wrong-version claim and two synthetic instruction-injection attempts.

All labels start as **pending human review**. Proposed labels and rationales were prepared by the assistant, checked against pinned source excerpts and kept separate from the model inputs. That is useful preparation, but it is not independent human ground truth.

## The two kinds of judgment

**Support** asks whether the provided excerpt establishes a claim. A fact can be true in the world and still be insufficiently supported by the selected source.

- supported: the entire claim follows from the evidence, within its stated scope.
- contradicted: the evidence establishes a conflicting fact.
- insufficient: the evidence does not establish the claim, but does not necessarily establish its opposite.

For example, evidence saying “timeout is 30 seconds” supports that value, contradicts “timeout is 60 seconds”, and is insufficient for “the service is healthy right now”. Evidence for demo-v1 is not automatically evidence about demo-v2.

**Correctness** compares the answer to the question and reference. Equivalent phrasing is allowed; changed facts, meaningful omissions and contradictions are not. It should not require the answer to copy the reference wording exactly.

Some examples are deliberately challenging. If a proposed label is ambiguous, use review notes or skip it rather than approving automatically. Cases needing substantial rewrites can be edited in eval/judge_cases.json before their review is approved.

## Your next hands-on step: review the calibration examples

From LLM_Project, run:

```powershell
.\.venv\Scripts\python.exe calibrate.py review --split calibration --reviewer spark
```

The command displays one case at a time: its question, claim/evidence or answer/reference, proposed label and rationale. It does not call the model, so the model server need not be running for review.

- Read the example and source first.
- Press Enter to accept its proposed label after reviewing it.
- Type a listed label to correct it.
- Type s to skip or q to stop.
- After accepting/correcting, optionally add a note; Enter leaves the note empty.

Approvals are saved after each case with your reviewer name, chosen label, optional notes and UTC timestamp. Run the command again to resume at the next pending case. Start with a few cases; you do not have to review all 48 in one sitting.

The review command records your decisions. It does not prove that those decisions are correct; a second reviewer would improve confidence.

## Run an assessment

For an exploratory diagnostic before review, keep the local model server running and use:

```powershell
.\.venv\Scripts\python.exe calibrate.py run --split calibration --draft
```

This explicitly uses proposed labels for pending cases and reports DRAFT_DIAGNOSTIC. Exit code 0 means the diagnostic completed; it does not mean thresholds passed or labels were approved. Judge errors produce exit code 2.

After all calibration labels have been reviewed:

```powershell
.\.venv\Scripts\python.exe calibrate.py run --split calibration
```

Normal runs are blocked while any selected label is pending. Each run uses a new output directory under runs/ and saves the exact selected examples, thresholds, prompts/schema hashes, model API identity, predictions, raw judgments, timing and report. No answers are generated by the RAG pipeline here: the judge is evaluating fixed example inputs.

The runner uses the same current correctness prompt, support prompt and output schemas as evaluate.py. The existing support prompt was extracted into a constant without changing its wording. The production answer pipeline is unchanged in this step.

## Read the results

The Markdown and JSON reports contain:

- A confusion matrix for each task: gold/proposed labels in rows, judge predictions in columns.
- Per-class precision, recall and F1 in JSON, and macro-F1 in the report overview.
- Bad-case detection recall: how often unsupported/contradicted claims or incorrect answers are rejected.
- Good-case acceptance recall: how often supported claims or correct answers are accepted.
- False acceptance rate, model errors and a list of disagreements.

The predeclared initial targets are macro-F1 >= 0.80, bad-case detection recall >= 0.85, good-case acceptance recall >= 0.85 and zero judge errors, for both tasks. Bad-case detection pools contradicted/insufficient for rejection recall, while the three-class macro-F1 still penalises confusing those labels.

Errors are included as missed classifications, never silently dropped. Empty required classes, missing results, changed labels within a result set and invalid thresholds cannot pass assessment.

These are small, related example groups; individual rows are not independent statistical observations. Review disagreement examples, rather than treating one aggregate score as proof of reliability.

## Keep validation separate

Calibration and validation have disjoint claim families/topics. Tune rubric/model choices using calibration examples. Review validation labels independently of the judge predictions, freeze the chosen judge, then assess validation once.

When ready, review validation with:

```powershell
.\.venv\Scripts\python.exe calibrate.py review --split validation --reviewer spark
```

Then run:

```powershell
.\.venv\Scripts\python.exe calibrate.py run --split validation
```

Draft validation runs are deliberately blocked. Do not repeatedly tune on validation results and continue calling the same set held out. Keep unused validation cases out of prompt examples. Both splits derive from existing development topics, so this is validation of the judge task, not a new held-out RAG question benchmark.

Even reviewed validation targets being met does not automatically enable semantic release gates. That integration is a later explicit step, binding the selected judge model and prompts to the assessment. The current evaluator continues to mark semantic scores uncalibrated.

## Files and scope

- calibrate.py: interactive review and model assessment.
- eval/judge_cases.json: 80 proposed examples and review records; track in Git.
- eval/judge_thresholds.json: targets specified before assessing the model.
- test_calibrate.py: tests for metrics, label leakage, review state and blocked unreviewed validation.
- runs/judge-.../: generated reports, predictions and frozen run inputs; ignored by Git.

Source excerpts are verified against the pinned corpus before a model run. Synthetic injected instructions are explicitly marked and retain the authentic source excerpt separately. Code in evidence is never executed by the calibration runner.

The generator, runtime verifier and judge currently share the same 4B model. Exact model binary hashes, model/driver reproducibility, larger independent review, confidence intervals and a separate held-out end-to-end question set remain future work. Keep old development baselines and Improvement.md unchanged.
